# ADR-320: OpenEnv Arena daily submission flywheel and Darwin search lane

**Status**: Proposed  
**Date**: 2026-10-09 (updated the same day after the first scored run, a local codex review and the cross-run analysis); updated 2026-10-10 after the second scored run  
**Scope**: `integrations/openenv-arena-darwin/**` (branch `feat/openenv-arena`)  
**Related**: ADR-277 (Autogenous adapter), ADR-279 (flywheel sequential evidence), ADR-317 (independent review isolation), ADR-319 `openenv-arena-curriculum` (environment lane, PR #383 — not duplicated here)

## Context

The OpenEnv Arena trains a fixed model (`Qwen/Qwen3.8-27B`, rev `1d4bf0f2`) with a fixed GRPO recipe on a submitted environment image plus task list, then scores it on 40 private tasks (5 per domain, 8 domains, one attempt each). One accepted submission per Hugging Face account per rolling 24 h. The leaderboard keeps **each domain's best result across an account's runs**.

Measured so far (public leaderboard and public Trackio metrics, 2026-10-09; 8 evaluated runs when first written, 11 at 16:30 EDT):

- The untrained model solves 4/40 (industrial 2, office 2).
- Our first run (`metaharness-mix8-20261009`, 274 updates) scored 4/40: office 3, software 1, industrial 0. Its office 3 is the highest single-domain score of any run.
- Through the first 8 runs no run had solved a task in science, finance, math, security or media. Runs 9–11 added one finance task (akseljoonas `mimo-curriculum-v3`, median training reward 0.00, 5% informative steps) and one security task (NoeFlandre `audit-trail-v1`, 23% informative steps). Science, math and media are still 0 for every account. The finance point came from a run that barely trained, which is consistent with sampling variance; with this sample size it cannot be told apart from a real gain.
- Best-per-domain totals at 16:30 EDT: akseljoonas 6/40 and NoeFlandre 6/40, each **over two runs** (no single run above 5/40); ruv 4/40 over one run. Part of the gap is therefore the number of draws, not the quality of any one run.
- Industrial stayed at 2 in 3 of the first 8 runs, all with fewer than 20 informative steps (`frac_reward_zero_std < 1`). Ours had 144 informative steps (53%) and lost it. With eight runs this is an observation, not a causal finding.

Two lanes exist: the environment lane (image, task generators, `calibrate.py`, `submission.py`, PR #383) and this lane (search, gate, GPU execution, daily submission). Their ownership boundary is part of this decision.

## Decision

1. **Daily submission flywheel** (`flywheel/`): render → pre-submit checks on the exact image digest → pure `decideSubmit` → POST → report. Every check blocks independently and fails closed; the HF token is read in-process only, never printed, stored or passed on a command line. Nothing is installed or auto-enabled by default.
2. **Policy** (`policy: gate-only | daily-best`). `gate-only` is the default and unchanged. `daily-best` submits the Flywheel-gate-promoted candidate when one exists with a verified receipt; otherwise a **re-draw** of the arena-validated incumbent. A re-draw is labelled selection on noise, never an improvement claim.
3. **Re-draw = the stored validated request body, verbatim, under a fresh `submission_id`.** The body is stored content-addressed and read-only (mode 0400); at use time its file digest and canonical digest must equal the recorded `request_sha256`, read without following symlinks. Hand-curated requests (not expressible as a Darwin genome, e.g. mix8) are therefore re-drawable.
4. **Verbatim check mode** (`render-and-check.mjs --request-json`): anonymous pull of the exact digest, `openenv validate --url`, live `/schema` equality, arena limits, native replay of every task id, on the request's own image. Per-task `image` fields are refused because they would not be checked.
5. **Offline bootstrap** (`bootstrap-incumbent.mjs`): seeds the incumbent only from the exact request, its receipt and an operator-fetched `validated` status; no network, no token path; refuses digest, receipt, id, date, rejection-history and pending-submission mismatches.
6. **Body-only incumbents skip GPU, search and the gate** (no genome to search from). This is a consequence to review, not a neutral default.
7. **Evaluation regime.** Cell measurement defaults to thinking **off** (the arena's apparent training regime, inferred from public completion lengths — unverified by the arena). Thinking mode is part of the cell-key provenance.
8. **Submission strategy under best-per-domain scoring** ("bank first, push later"): while industrial 2 is not banked, submit a low-drift, single-task office run (`office_reconciliation-d3`) on the same image as mix8; push trained domains afterwards. This is a hypothesis from eight public runs, to be judged on its outcome.
9. **Review.** The environment lane's review of this lane is input, not approval; submission authority comes only from the owner's standing approval plus the mandatory checks. Local `codex exec` (read-only by default) replaces the Slack ChatGPT agent as reviewer per the owner's instruction of 2026-10-09; granting it write access to environment-lane files is not decided here. Its first review found three gaps, all reproduced and fixed test-first in `978ab069`: (a) a `validated` status for an id that already existed on the arena (receipt `post_attempted:false`, payload unverifiable) could install our local body as the incumbent — the incumbent is now installed only when the durable receipt proves this flywheel POSTed the pending digest, otherwise nothing is written and a needs-human note is recorded; (b) a crash between the arena accepting the POST and the receipt reaching `recorded` left the receipt unfinished — a proven receipt is now healed to `recorded`, never re-POSTed; (c) verbatim mode coerced a non-string `submission_id` — it must now be a string. Known and left: a narrow race (a rival creating the same id between the preflight GET and our POST would still match a trusted receipt; the arena answers 4xx for it), and smaller validation differences from `submission.py` (UTF-16 name length, trailing-newline regex) that fail closed.
10. **Submission operator.** `flywheel/codex-submit.sh REQUEST.json [--execute]` is the single checked path: it refuses to run before the slot opens (prior receipt `accepted_at` + 24 h), runs the verbatim pre-submit checks, and passes the checked request's canonical sha256 to the environment client's `submit` (dry run without `--execute`). Local `codex exec` runs this script as the operator; the HF token is read in-process by the environment client and is never given to, printed by, or stored by codex or the script. A codex dry-run rehearsal passed end to end with `workspace-write` plus network access (Docker worked in that sandbox). The orchestrating session verifies the receipt and arena status afterwards. The script is new and has not yet been used for a real submission.
11. **Calibration routes.** Hosted inference through the Hugging Face router serves `Qwen/Qwen3.8-27B` (Novita $0.42 in / $3 out per million tokens; OVHcloud slightly more). The owner's account first returned HTTP 402 (no inference credits); after the owner enabled HF PRO the same route returned 200, and thinking-off is verifiable from usage (`reasoning_tokens` 0 with `chat_template_kwargs.enable_thinking=false`, 20 without). Calibration through the router is the default route now: about 3,000 tokens and under a cent per episode, driven by `calibrate.py` with a hard per-call token ceiling (`--max-total-tokens`) and a per-test spend ledger. The provider's checkpoint cannot be confirmed to equal the arena's pinned revision. A rented GPU (about $11, existing watchdog and ledger) remains the alternative for exact-checkpoint work. Neither affects the daily submission.
12. **External coordination.** An open invitation was posted on the arena board (#82, corrected by #83) pointing to the open federation at `https://x.ruv.io` (self-registration as `member`, NIP-98 auth, rate limited; public channels `pub:announce`, `pub:help`, `pub:claims`, `pub:showcase`). It offers measured, public material only (cross-run informative-step table, the pre-submit check code, a labelled local-probe note) and nothing private; each account still submits and is scored on its own.
13. **Next environment image (v4, not part of the daily submission).** A reply-format clause (`REPLY_FORMAT`, 166 characters) appended to the reset prompt only, in the isolated worktree `~/projects/metaharness-arena-v4` (branch `feat/openenv-arena-v4-env`, uncommitted): task instances, answers, grading and the random stream are unchanged and the frozen 768-instance test passes unmodified (147 tests, 802 subtests). Measured 2026-10-09 with the lane's `calibrate.py` client through the Hugging Face router (`Qwen/Qwen3.8-27B:novita`, thinking off, honoured: 0 reasoning tokens), paired on identical seeds, 16 cells (8 families × d2/d3) × 8 seeds × 2 arms = 128 pairs, estimated spend $0.31 of a $2.00 cap: without the clause 48% of replies were schema echoes (74 of 128 episodes had an invalid reply, mean reward 0.031, 1 solved); with it 98.8% of replies were valid (3 of 128 episodes with an invalid reply, mean reward 0.185, 4 solved); paired mean reward difference +0.154, 95% bootstrap CI [+0.109, +0.199] (clause better in 50 pairs, worse in 5). **Limits:** the calibration client's system prompt is not the arena trainer's, which is unknown to us; on office_reconciliation-d3 the no-clause arm scored 0.00 and the clause arm 0.50 while the real arena run's first-half reward on that task was 0.54, so the arena's own prompting appears to resemble the clause arm and the clause's effect in the arena is probably much smaller than in this client. Earlier thinking-off "dead cell" calibrations that used this client without the clause were partly schema-echo artifacts (e.g. math, security and software cells scored 0.00 without it); industrial and media stay dead with it (0.00–0.03). A new image would need calibration, a registry publish, the pre-submit checks and review before any submission. A `software_patch` task family (injected-bug repair with hidden tests) is designed but not built.
14. **Unattended fallback for the daily slot.** The loop jobs that drive the primary path are session-only, so a one-shot systemd user timer (`arena-submit-fallback`, 2026-10-09 20:47:30 EDT, about 6.5 minutes after the slot opens) runs the same `codex-submit.sh … --execute` directly (no model in the loop). It was first run in dry-run mode under systemd to prove its environment (Docker, Node, Python, token file). The script's receipt guard makes a second attempt reconcile-only, never a second POST, so the primary and fallback paths cannot double-submit. The machine cannot suspend (suspend and hibernate masked) and user services persist after logout (lingering on). Cancel with `systemctl --user stop arena-submit-fallback.timer`.
15. **Second submission and run lifecycle (2026-10-10).** The office-only request `metaharness-office-20261010` (sha256 `b8607a8c…`) passed every pre-submit check on the exact digest and was posted by the slot's opening second through `codex-submit.sh --execute`, run by hand from the session. It was not run through `codex exec`: a sandboxed codex has no network, and the script is built to be run either way. The arena accepted it at 00:41:02Z (HTTP 202; `validated`, slot `used`). The fallback timer was then stopped. **Timeline correction:** the run is created within seconds of acceptance (`created_at` 00:41:16Z) and trains for the whole budget (`budget_s` 14400; this run stopped after 265 updates, 3.48 h), then its evaluation is queued (04:09:59Z) and finishes in about 10 minutes (04:19Z). During the session the evaluation start time was first misread as the training start (suggesting a run "starts about 3.5 hours after acceptance"), and a status reader printed a nonexistent field (`run`) instead of `run_id`; both were corrected from the run's own `created_at`, `budget_started_at` and `evaluation` fields. The `run_id` is written to the receipt when `status` reconciles it. Reading a run needs the token in-process (`GET /api/openenv/runs/RUN_ID`); its Trackio metrics are public (`POST /api/get_run_summary`, `/api/get_metric_values`).
16. **Disclosure boundary.** Publish measurements (scores, `completions/clipped_ratio`, `frac_reward_zero_std`, run state) with the noise caveat. Hold exact prompt or format-clause wording, task generators, seeds and verifier logic until the run that uses them has been evaluated. Keys and credentials never go into a message, repository or ledger. We make no claim that operators respond to our posts or that we set the board's agenda; neither is observed.
17. **Paired reply-format test on rented hardware (in progress 2026-10-10).** Reuses the flywheel's `gpu.mjs` lifecycle unchanged (pinned vLLM v0.31.0 image digest, offer filter, worst-case spend ledger written before create, label watchdog armed before create, confirmed destroy), with the total cap at the owner's $250 and a 25 USD day cap. One 80 GB instance at 1.11 USD/h (planned worst case 4.71 USD for 4.25 h) serves `Qwen/Qwen3.8-27B` at the arena revision. `bench3.py` runs four arms on shared seeds (V0 current prompt; V1 reply-format clause; V2 clause plus a re-check line; V3 clause plus an exact-keys-and-types line) across all eight task families and three difficulties, thinking off, 12 seed blocks (about 4,600 episodes). The aim is twofold: whether any variant moves solve rate or format-failure rate beyond the ±0.1 noise, and which family/difficulty cells of the four domains we score 0 in (cybersecurity, finance, mathematics, natural science) sit at a 20–80% pass rate, where GRPO can learn. **Result (2026-10-10, instance `rfpaired-b`, 1.0 h, settled 0.99 USD; the first attempt `rfpaired-a` failed in 0.64 h, settled 0.71 USD, because vLLM aborted with `max_num_seqs (1024) exceeds available Mamba cache blocks (674)` on this hybrid-attention model; the fix is `--max-num-seqs 128`).** 1,152 fully paired episodes per arm. Under the calibration client's strict action parsing, the current prompt (V0, the arena image as submitted) ended in `invalid_json_action` in 1,068 of 1,152 episodes (93%), against 4 of 1,152 with the reply-format clause (V1). Pooled mean reward 0.014 to 0.179 (paired difference +0.165, 95% CI +0.150 to +0.179); full solves 0.3% to 2.5% (+0.022, CI +0.012 to +0.031). V2 (re-check line) and V3 (exact keys and types) add nothing over V1 (reward -0.003 and +0.003, both CIs include 0). Under V1, partial credit exists in the four domains we score 0 in (mean reward: math_route d1 0.38, finance_ledger d1 0.24, security_triage d1 0.17, science_calibration d1 0.07) but full solves are about 0-2%; the cells with usable solve rates are office_reconciliation d2 25%, software_change d1 15%, office d1 12.5%. **Limit:** thinking off, local server, the calibration client's parser. The arena's own training reward on `office_reconciliation-d3` was about 0.51-0.56, which matches V1 locally (0.51) and not V0 (0.04), so the arena's rollout probably does not suffer the strict-parse failures and the clause may change little there; this inference is unverified (operator question #115 about the rollout parser is unanswered).
18. **Paired-benchmark toolkit, reward-hack guard and a launch fix (2026-10-10).** The benchmark from decision 17 is now tracked in `eval/paired/` as Node modules with tests (`paired-bench.mjs` config-driven, resumable runner that accepts only a loopback server; `paired-analyze.mjs` paired bootstrap with a per-cell pass-rate table; `paired-vast.mjs` wrapping `flywheel/gpu.mjs` so teardown always runs and the benchmark window is clamped inside the rental window; `trajectory-scan.mjs`; `lib.mjs`). A golden test reproduces the archived result: pooled reward difference +0.165 (95% CI +0.150 to +0.180), the three variants' means 0.014 / 0.179 / 0.177 / 0.182 and the baseline's strict-parse failure rate. **Launch fix:** `flywheel/gpu.mjs` defaulted to vLLM's `max_num_seqs` of 1024, which aborts engine startup on this hybrid-attention model; the default launch now passes `--max-num-seqs 128` and `gpu.test.mjs` asserts it, so the daily flywheel would have failed the same way as the first rental. **Reward-hack guard:** the MetaHarness monitor (`packages/weight-eft`, also reachable as `metaharness_reward_hack_scan`) reads OpenAI-style `tool_calls` and tool responses, while arena trajectories carry actions as plain assistant JSON, so run unchanged it inspects nothing and always reports clean. An earlier note that it "returned clean on an arena trajectory" was therefore vacuous and is withdrawn. `trajectory-scan.mjs` converts arena actions into tool calls (`read` to `read_file`, `list` to `view`, observations to tool responses); tests include positive controls that a gold-path read, an oracle marker in an observation and a path outside the sandbox are each flagged. Over the 4,608 archived benchmark episodes it inspected 9,276 actions (368 in the baseline arm, where most replies were not valid actions, about 2,300 in each other arm) and flagged none; the arena environments expose no shell and no answer files, so a clean result is the expected one. It is a regression guard, not evidence of robustness. Of the other RuVector capabilities reviewed (198 crates), none addresses the binding constraints (a noisy 40-task evaluation, steps without reward variance, no proxy that predicts arena gain): `ruvector-sota-bench` benchmarks ANN recall and throughput on synthetic vectors, `ruvector-domain-expansion`'s transfer claims are unverified at language-model scale, `ruvector-retrieval-receipt` detects only post-issuance mutation, and the sparse-attention crate is an inference-only edge kernel.
19. **Held-out discipline, a local training testbed, and what `completions/clipped_ratio` means (2026-10-10).** Instance seeds are split into disjoint ranges in `eval/paired/splits.mjs` (held-out test 900,000-909,999; cell-selection measurements 910,000-919,999; training 2,000,000-2,999,999) and `paired-bench` refuses a run whose seeds fall outside the range it declares, so choosing training cells can never see the instances they are judged on; a family-level split supports a stricter cross-family transfer test. `paired-bench` gained `repeats` (re-sample the same instances) and `paired-analyze --learnability` reports per cell the share of instances whose repeat samples differ, which is the quantity GRPO needs (a group that scores identically gives no advantage). `flywheel/gpu.mjs` gained `excludeOffers` and `excludeMachines` after two rentals stalled (one host pulled the image for over 15 minutes; one accepted the SSH key only after about 12 minutes), both with tests. **Clipped ratio:** the arena's Trackio metric names (`completions/clipped_ratio`, `frac_reward_zero_std`, `entropy`, `clip_ratio/*`) are TRL GRPO trainer names, and in TRL 1.15's source a completion is counted as clipped when its last token is not an end-of-sequence or padding token. A multi-turn completion that ends on environment tokens (a final observation appended after the model's last action) is therefore counted as clipped, which explains a ratio near 1.0 in nearly every public run regardless of completion length. It is a metric artifact of how the rollout is structured, not a limit hit by our environment. **Checked against the arena's own Trackio metrics (2026-10-10):** `grad_norm` is non-zero on exactly the steps where `frac_reward_zero_std` is below 1 and zero on every all-zero-variance step, with the median clipped ratio at 1.0 in both runs (mix8: gradient on 144 of 274 steps, 130 all-zero-variance steps and none with gradient; office-only: 64 of 265, 201 all-zero-variance and none with gradient). Clipped completions therefore still reach the loss, so `mask_truncated_completions` is not masking them and the clipped ratio is a metric artifact of multi-turn episodes. Another entrant (rca-umb, board #123) reported the same pattern independently. **Consequence for design:** the 8-task list gave 53% of steps with gradient and the one-task list only 24%, so a single-task training list costs learning signal; it is the low-drift choice, not the learning choice. The flat scores are not explained by masking. **Local testbed:** a TRL GRPO prototype with a custom `rollout_func` (`env_mask` on the model's tokens, the arena's JSON-action protocol) runs end to end on the workstation GPU with a small model, but Qwen3-1.7B scores zero on the families tried and mostly exhausts its turn budget reading files, so a small model gives no learning signal here and only the 27B on rented hardware does. Incident: a run stopped by hand during a slow boot was in fact about to start and the orchestrator was killed without teardown; the instance was destroyed through the ledger helper, which settles an orphan at its full plan (3.22 USD for 0.27 h), so the ledger overstates spend in the safe direction.
20. **Acceptance rule for reward-shape and prompt changes (2026-10-10).** Reward density, reward variance and behavioural improvement are separate properties: a group scoring [0.5, 0.5, 0.5, 0.5] has zero relative advantage however dense the reward, which is what run 2 looked like (reward near 0.5, about 69% of steps at zero variance). The arena's contract accepts exactly one JSON action per reply and a malformed reply ends the episode (the request's `finish_action` grades the state already reached), so the environment cannot repair a rejected message; its only format lever is the reset-prompt clause. Methods that act on the trainer (entropy advantage shaping, SFT warm-up) or on generation (constrained decoding) are outside our control; GRESO-style selection can be borrowed for local experiments, noting that it revisits previously uniform prompts, so a static cell filter only approximates it. Observation budgets are set for the whole episode (the declared completion and context tokens), not per observation, and truncating observations is wrong where a task needs every source read. **Rule:** a change to reward shape (binary versus partial credit) or to the prompt is adopted for an arena entry only after a paired comparison under identical model settings and compute budgets shows better success on unseen failure structures (held-out seeds and, for transfer, held-out families) without added safety violations; a lower share of zero-variance groups alone is not sufficient. Verifiers stay protected (the agent only sees files) and `trajectory-scan` stays as a regression guard against shortcut learning. The binary-versus-partial comparison needs the local 27B training testbed, which does not exist yet, so until it does no such change enters an entry on expectation alone.
21. **Learnability map of the 24 family/difficulty cells (2026-10-10, select split).** One rented instance (0.59 h, settled 0.70 USD) sampled each of 16-20 task instances per cell about 8 times with the reply-format clause (V1), thinking off, temperature 0.7 in the calibration client, 960 calls and no non-zero exit codes. 104 of the 960 output files held provider failures from an aborted earlier attempt (the old resume logic counted them as finished; it now re-runs any file with a provider failure) and those episodes are dropped, so media, software, security and finance cells have 16-19 instances instead of 20. "Mixed" is the share of instances whose repeat samples do not all score the same, the quantity GRPO needs. Results: finance 83-85% mixed (mean reward 0.21-0.25), math 70-95% (0.14-0.29), security 81-100% (0.08-0.23), science d1/d2 75-85% (0.06-0.09) and d3 55%, software 81-88% (0.09-0.39), office 45-55% (0.52-0.57), industrial 20-50% mixed with mean reward under 0.04, media 6-44% mixed and mostly all-zero (0.00-0.05). No cell has groups that are all solved, and full solves are rare everywhere. Reading: partial-credit variation exists broadly, including in the four domains where we score 0, so zero-variance steps are not an unavoidable property of these families; the arena's observed zero-variance steps in the office-only run (201 of 265, 76% over the whole run, against 69% over the last tenth of steps that I first reported) are in line with office d3 being 45% mixed here. What the map does not show: that variation in partial credit turns into full solves, that training moves any of it, or that the arena samples the instances we would choose. It is a selection aid, to be confirmed by the acceptance rule in decision 20. Raw table: scratchpad `learn1/learnability-prelim.json`.
22. **27B training smoke test (2026-10-10, `smoke27b-a`, settled 0.20 USD for 0.20 h).** `eval/train/train-vast.mjs` rented a shell on an A100 80GB PCIe (1.03 USD/h; the filter accepts any card with at least 78 GB, so an 80 GB card is the tight case), installed torch 2.13 (cu130), transformers 5.17, trl 1.15, peft 0.21 and flash-linear-attention in 30 s, downloaded the pinned revision (55.6 GB, about 10 min), and ran two TRL GRPO steps with LoRA r=16 (attention and MLP projections), one prompt and four samples per step, up to six turns, thinking off. Result: the 27B fits and trains, peak GPU memory 53.3 GiB (51.4 after the first rollout), 79 s per step (rollouts 53 s and 31 s for four episodes averaging 2 turns and 682 and 1,288 tokens, generated with Hugging Face `generate`); the loss was 0 and grad_norm 0 on both steps because every group scored identically (0.0 and 0.5), the same zero-variance behaviour seen in the arena. Not measured: any learning (two steps on uniform rewards), whether the linear-attention fast path was used (the kernel package installed; speed was not compared with the fallback), and throughput at a realistic batch. Extrapolation, labelled as such: 32 episodes per step (8 samples by 4 prompts) is about eight times the rollout work, so roughly 4-7 min per step, or 7-12 h and 7-12 USD per 100 steps; rollouts dominate, so a vLLM-based rollout would be the next optimisation. The runner downloads results and tears down even on failure, covered by tests.
23. **Pre-registered held-out learning experiment on the 27B (2026-10-11, written and committed before any rental).** Question: does the fixed recipe, trained on a mixed task list for roughly one fifth of an arena run, raise the full-solve rate on instances it never saw (H1) and on families it never trained on (H2)? Reward shape (binary against partial) is not tested here; it is experiment 2, run only if H1 holds, under decision 20. Setup: `Qwen/Qwen3.8-27B` revision `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`, LoRA rank 16, HF generate, thinking off, the environment's own (partial) reward, 40 steps of 2 prompts times a group of 8, at most 6 turns, learning rate 5e-5 (a recorded deviation: the arena's reported constant 5e-6 runs about 265 updates, so a roughly 5 times shorter run gets a higher rate to compensate). Training families `finance_ledger`, `math_route`, `security_triage`, `science_calibration` at difficulties 1 and 2, seeds from the train range [2,000,000, 3,000,000). Evaluation, every episode on held-out seeds 900000-900015 (16 instances per cell, one sampled reply stream each, T=1.0, identical instances for both tags, base evaluated in the same process through the same code path before training; the LoRA B matrices start at zero so it is the base model): H1 set = the four training families at d1 and d2 (128 episodes); H2 set = `software_change`, `office_reconciliation`, `industrial_schedule`, `media_timeline` at d1 and d2 (128 episodes). Decision rule: paired bootstrap, 95 percent, via `eval/paired/paired-analyze.mjs --compare trained:base`; H1 or H2 counts as supported only if the lower bound of the full-solve difference is above 0 on its set. Also reported: mean-reward difference, bad-reply rate and the reward-hack scan on trajectories. With 128 pairs at base rates near 0.1-0.3 the interval half-width is about 0.06-0.08, so only a lift of roughly 0.10 or more is detectable; a null means no detectable effect at this scale, not that the recipe cannot learn. Actions: H1 and H2 supported -> tonight's entry uses the mixed list (task list only, rewards unchanged), then experiment 2; H1 only -> the mixed list is still preferred on gradient grounds (53 percent informative steps against about 25 percent for office-only) but no transfer is claimed; H1 not supported -> no change to the default and no more spend on this axis, the next lever is task diversity and difficulty, not reward shape. Tonight's standing-approval entry runs on its own track with the same default and is gated on this result only if the result arrives before 19:30 EDT. Cost: planned under 15 USD against the 250 USD cap, worst-case ledger row before create, ledger about 7.7 USD so far. Harness: `eval/train/grpo_arena.py` gained `--reward-mode`, `--eval-split` and the other `--eval-*` options, `--eval-only`/`--adapter`, and adapter saving; evaluation rows use the paired toolkit's layout, and a local Qwen3-0.6B smoke ran through the analyzer unchanged.
24. **Result of the decision-23 experiment (`learn27b-2`, 2026-10-11, settled 1.56 USD; the first attempt `learn27b-1` failed at its first ssh step and settled 0.08 USD).** 40 steps took 2067 s (51.7 s per step, peak 60.3 GiB); each 256-episode evaluation took about 400 s. Paired by seed, 128 episodes per set, 95 percent bootstrap. H1 (training families, unseen seeds): full solves 0/128 before and 0/128 after, so H1 is NOT supported by the pre-registered criterion; mean reward rose from 0.124 to 0.288 (+0.163 [+0.118, +0.209]) and episodes with a bad reply fell from 5.5 to 0.8 percent. Per cell the reward gain is clear for `security_triage` (+0.33 to +0.40) and `finance_ledger` (+0.14 to +0.16) and within noise for `math_route` and `science_calibration`. H2 (families never trained on): full solves 4/128 (3.1 percent) before and 10/128 (7.8 percent) after, +0.047 [+0.008, +0.094], so H2 IS supported by the pre-registered criterion; mean reward +0.066 [+0.025, +0.109]; bad-reply episodes 7.0 to 3.9 percent. The solves sit in `office_reconciliation` and `software_change`; no single cell is significant on its own. ## What the cross-run data and the state of the art say about this architecture

Not a validation of the design; an honest limit on it.

- **Learning versus score.** Comparing early and late training reward across the 11 runs, only NoeFlandre's `audit-trail-v1` shows a clear rise (0.40 to 0.55, +0.13); most others moved by 0.01–0.05, several starting already saturated (0.96–0.99). Ours moved +0.03 overall (math d3 0.16 to 0.27 by halves) despite the highest share of informative steps (53%). The share of informative steps shows no visible relationship with the change in evaluation score across the 11 runs (our 53% gained nothing; NoeFlandre's 4% run gained a point). The runs that gained a point over the untrained model barely trained, consistent with sampling variance on five tasks per domain with one attempt each. This is a small sample and does not rule out a real effect.
- **Outcome of the second run and the clipping signal.** `metaharness-office-20261010` evaluated 4/40 (industrial 1, media 1, office 1, software 1), equal to the first run's 4/40 with a different per-domain mix; the leaderboard's best-per-domain rule gives the account 6/40 (office 3, industrial 1, media 1, software 1), a tie with the two leaders, not a lead (7 is needed). The 6 comes from combining two runs. Its Trackio showed reward 0.51 to 0.56, `frac_reward_zero_std` 0.81 to 0.69 (most steps carried no learning signal) and `completions/clipped_ratio` about 1.0 (first run 0.99). The declared `completion_tokens` (12288) is far above the longest completion (about 195–220 tokens), so our declared limit is not what clips. Other public runs show the same near-1.0 ratio at very different lengths (NoeFlandre longest 30 tokens, burtenshaw 337, Louistiti about 300) while the one run with long completions (akseljoonas, about 1,300–1,700 tokens) shows 0.07–0.13. That points to how the arena ends a turn rather than to a defect in this environment, but it is not verified; operators have not answered the related questions on the board. Two of the three other runs evaluated in the same window scored below the 4/40 untrained reference (2/40 and 3/40).
- **No validated proxy fitness.** The Darwin search and the Flywheel gate need a cheap pre-submission measure that predicts arena improvement; none has been shown to. The paired test above showed the calibration client's behaviour differs from the arena's, which weakens calibration as a proxy.
- **State of the art (abstract and search-summary level, not full-paper reads).** Serious pipelines use many programmatically generated environments with verified oracles (Agent World Model about 1,000 environments; RLVE 400 with adaptive difficulty; Reasoning Gym 100+ generators; SWE-smith about 50k instances), difficulty filtering around a middling pass rate (DAPO dynamic sampling, learnability filtering), and quality gates (oracle must score 1, hidden tests, named reward hacks). Reported held-out gains are modest even then (Envs-FORGE about +2 points over the best fixed recipe), more distinct environments transferred better in RLVE, and a 2026 study reports a generalization tax for narrow agentic RL (held-out environments degrade while in-domain scores rise). No source found tests whether proxy fitness predicts held-out gain at a few noisy evaluation tasks.
- **Consequence for the design.** Treat the contest score as a coarse check, not a fitness function; measure progress on our own held-out set of 100+ tasks from different generators with many attempts; prefer task families with randomized variation over tuned fixed lists; change one variable per submission. These are inferences from the sources, not adopted work items.

## Considered and not done

- **No-learning "bank" environment** (an environment designed to produce almost no gradient so the run returns roughly the base model's industrial 2). Plausibly effective, but it exploits the scoring rule rather than the contest's intent. Not used; left as an explicit owner decision.
- **ruvllm local proxy** for calibration: dropped; candle has no Qwen3.5/3.8 hybrid architecture, so a proxy would not measure the arena's model.
- **Failure clustering (ruvector)**: deferred until more scored runs exist.
- **posttrain.com "PostTrain Arena" (`openenv-9b`)**: a different submission type (collections of 1–200 task packages: `task.md`, Dockerfile, verifier, oracle; scored by the change in held-out pass rate after training, mean over organizer-accepted runs). Its runs are stated to be paused. Not used; our work does not transfer as-is, and the ranking wording differs from the arena guide, which still says each domain keeps the highest score across runs. Exporting our finance, industrial and media families as task packages is a possible later experiment.
- **Public harness leaderboards**: a research pass found only GAIA and Online-Mind2Web accept agent-harness entries on Hugging Face; SWE-bench lives on GitHub; the repo's own best numbers are SWE-bench Lite 51.3% (154/300) and Verified 55.6% (278/500), self-run with the official scorer and not independently verified (the Lite submission, SWE-bench/experiments PR #453, is open). No GAIA measurement exists. The 58.3% Lite figure uses a gold-test oracle and is not a leaderboard result. No decision to submit anywhere is taken here.

## Consequences

- Positive: daily draws compound under best-per-domain scoring; a weak run cannot lower the banked score; every submission is reproducible from stored bytes and hashed evidence.
- Negative / risks: re-draws are noise draws, not improvements; paired confirmation on rented GPUs is bounded by the owner's $250 cap (fail closed; raised from $200 on 2026-10-09); the promoted-candidate path still cannot bind the request digest into the gate receipt, so promoted days skip until that is fixed; days with refused GPU or failed search do not fall back to a re-draw.
- The primary path depends on the orchestrating session staying open at the slot time (the loop jobs are session-only); the unattended fallback in decision 14 covers a dead session. The flywheel's own daily systemd timer is deliberately not installed yet.
- Competitive context: four more environments aimed at the unscored domains (Derivation Check, Five Desks, Reconcile Lab, Shifting Desks) were public or in training on 2026-10-09, after Audit Trail produced the first security point; any further score there raises the bar. The office-only request of 2026-10-10 tied the two leaders at 6/40 through best-per-domain scoring; outright first needs 7, and the four domains where we score 0 are the cheapest place to find the seventh point.
- Open before enabling the timer: `checks.expectEnvCommit`, gate public key, seeding the incumbent from a validated submission, and a real submission through `codex-submit.sh`.

### Decision 27: pre-registration, learn27b-4 (binary reward on the only learnable cells, 2026-10-12)

- H5 replication: run A trained minus base, office_reconciliation + software_change at d1 and d2 pooled, dSolved lower bound above 0.

If H5 fails, the decision 28 gain is treated as unreplicated and no submission candidate is built from it. One run each, no re-runs or recipe changes after results are seen. What these intervals do not cover: variability across training seeds. Reliability across seeds comes only from comparing run A (seed 1) with decision 28 (seed 0), two seeds in total, which is thin; run B is also a single seed.

Research programme (overnight loop worker; each stage needs its own committed pre-registration and the budget above): 1) this decision. 2) Cell search: measure base full-solve rates on the `select` split at d1 to d3 for every family and mark cells with a base rate between 5% and 70% as binary-reward candidates; confirm any chosen cell on `confirm`. 3) Optimizer comparison: a frozen proposer picks the next recipe change from the evidence log (select-split and development results only; the `confirm` set stays inaccessible to it); compare it with an equal-budget random-search control and the hand-chosen recipe, by verified gain per GPU dollar on fresh task families, with predefined regression limits. 4) Only if the proposer beats the controls over two successive generations and several training seeds, call it bounded recursive improvement. Until then the evidence is targeted learning from a human-chosen recipe, not recursive self-improvement. The loop launches a stage only when its pre-registration is committed, caps allow it, and at most two GPU jobs run at once.

Note on reply parsing (2026-10-12): the arena guide (AGENTS.md, "How the model sees your environment") states that each reply must be exactly one JSON object and nothing else, and any other reply ends the episode. Strict scoring in our local runs therefore matches the documented rule. A third-party board report (#156) says the arena plays a sentence before the JSON; that conflicts with the guide and is unverified. The earlier caveat in decisions 27 and 29 that strict scoring may understate arena behaviour rests on that unverified report.
